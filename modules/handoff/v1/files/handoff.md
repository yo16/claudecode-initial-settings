# 停止するときに git と beads の状態を揃える

Claude Code のセッションは、いつ終了されてもよいものとして扱う。夜に終了して翌朝にまっさらなコンテキストで再開する、といった使い方を前提にする。そのため、作業の状態が変わったあとにターンを終えるときは、状況を beads の Issue と git に記録し、両者が同じ状況を指すようにする。記録せずに停止すると、次のセッションは何が終わって何が残っているか分からなくなる。

## 停止点

次のいずれかでターンを終えるときが停止点である。作業の状態が何も変わっていない、質疑応答だけのターンは除く。

- タスクが完了した
- ユーザーに質問や決断の依頼をして、返事を待つ
- エラーや情報不足で続行できない
- ユーザーから中断の指示があった

## 停止前にすること

最後のメッセージを書く前に、次を上から順に行う。

1. **Issue を現状に合わせる**
   - 完了した Issue は `bd close <id>` で閉じる。
   - 着手したが終わっていない Issue は in_progress のままにし、`bd note <id> "..."` で現状を追記する。書く内容は、終わったこと、残っていること、次にやること、関係するファイルの一覧。
   - ユーザーの返事を待つ場合は、何を質問していて、どの選択肢があるかを同じ note に書く。
   - 作業中に見つかった残作業や後回しにしたことは、新しい Issue にする（`bd create`）。
2. **git を Issue に合わせる**
   - 完了した作業は、git の運用ルールに従ってコミットし、push する。
   - 未完了の変更は、壊れた状態をコミットしないためにそのまま残してよい。ただし `git status` で変更のあるファイルを確認し、その一覧を該当 Issue の note に含める。
   - コミットしたときは、コミットの件名を該当 Issue の note に書く。
3. **両者が一致しているか確かめる**
   - `bd list --status=in_progress` に出る Issue と、`git status` に出る未コミットの変更が、どちらも note の記述と矛盾しないことを確認する。
4. **最後のメッセージに状況を書く**
   - 完了した Issue、進行中の Issue、ユーザーに求めていることを、Issue の ID つきで書く。

## 再開するときにすること

新しいセッションで作業を頼まれたら、着手する前に次を行う。

1. `bd list --status=in_progress` で進行中の Issue を確認し、`bd show <id>` で note を読む。
2. `git status` と `git log --oneline -5` で、未コミットの変更と直近のコミットを確認する。
3. note の記述と実際の状態が食い違っていれば、実際の状態を正として note を追記し、ユーザーに報告する。
4. ユーザーの返事待ちで止まっていた Issue があれば、返事の内容を確認してから進める。
