# GitHub Actions は無料枠を節約して使う

GitHub Actions の無料枠（実行時間と保存容量）は、リポジトリごとではなく、アカウントや Organization の全体で共有している。このリポジトリで使った分だけ、同じアカウントのほかのリポジトリが使える分が減る。ワークフローを作るときと変えるときは、消費を小さく抑え、使う分は効果のあるところに絞る。

## 枠の数え方

2026-11 時点の GitHub の課金の仕組み。設計の判断はこれを前提にする。

- 非公開リポジトリの実行は、アカウント共有の枠を消費する。公開リポジトリで標準ランナーを使う実行は、枠を消費しない。
- 実行時間は、ジョブごとに分単位へ切り上げて数える。10 秒で終わるジョブを 6 つ動かすと 6 分になる。
- ランナーの単価は OS で違う。Linux が最も安く、Windows は 2 倍近く、macOS は約 10 倍かかる。
- artifact の保存容量は GitHub Packages と同じ枠で、置いている時間に応じて消費する。既定では 90 日残る。
- キャッシュは別枠で、リポジトリごとに上限がある。

公開リポジトリでも、意味のない実行をしない方針は同じにする。あとで非公開にしても、そのまま使えるようにするため。

## Actions を使う前に

- ワークフローを足す前に、それが何を防ぐか、何を自動化するかを一文で言えることを確かめる。言えないものは作らない。
- 手元で済む検査は手元で行う。lint、整形、型検査、単体テストは、コミット前に Claude Code が実行すれば足りることが多い。同じ検査を Actions でも動かすのは、複数人が push する、PR を受け付けるなど、手元の実行を当てにできないときにする。
- ほかのサービスが既にしていることを重ねない。ホスティング（Vercel、Cloudflare Pages など）がデプロイのたびにビルドしているなら、Actions で同じビルドをしない。

## いつ動かすか

- 同じコミットに対して、同じ検査を二重に動かさない。`push` と `pull_request` の両方を指定するときは、`push` を `main` だけに絞る。
- `paths` か `paths-ignore` で、関係のない変更では動かさない。文書だけの変更でテストやビルドを動かさない。
- `concurrency` に `cancel-in-progress: true` を付け、新しいコミットが来たら同じブランチの古い実行を止める。デプロイのように途中で止めると困るものには付けない。
- 時間のかかる検査（E2E テスト、すべての組み合わせでのテストなど）は、すべての push では動かさない。`main` に入るときか、`workflow_dispatch` による手動実行に寄せる。
- `schedule` は、定期的に動かす理由があるときだけ使い、頻度は目的を満たす最小にする。変更がなければ結果が変わらない検査を、定期実行しない。

## ジョブの作り方

- ジョブを細かく分けない。切り上げはジョブごとで、checkout と依存のインストールもジョブごとにかかる。短い検査は、1 つのジョブのステップとして並べる。並列にすると待ち時間は減るが、消費は増える。
- ランナーは `ubuntu-latest` を使う。Windows と macOS は、その OS でしか確かめられないことがあるときだけ使う。
- `matrix` は必要な組み合わせだけにする。対応する版の下限と上限など、落ちたら困る組み合わせに絞る。
- すべてのジョブに `timeout-minutes` を付ける。既定は 360 分で、止まったままのジョブが枠を使い切る。普段の所要時間の 2〜3 倍を目安にする。
- 依存のインストールにはキャッシュを使う（`actions/setup-node` の `cache` など）。キャッシュのキーはロックファイルのハッシュにし、コミットごとに変わる値を入れない。
- 早く終わって失敗しやすい検査を先に置く。lint、テスト、ビルドの順にし、前の段で失敗したら後ろを動かさない。

## 保存容量

- artifact は、あとで人か別のジョブが使うときだけ保存する。調査用のログやスクリーンショットは、失敗したときだけ保存する（`if: failure()`）。
- artifact には `retention-days` を付け、必要な最短の日数にする。調査用なら数日で足りる。
- ビルドの成果物や大きなファイルを、置き場として artifact や GitHub Packages に溜めない。

## 作ったあと

- ワークフローを足したか変えたら、最初の実行の所要時間をジョブごとに確かめる（`gh run view` など）。想定より長ければ、その場で直す。
- ユーザーへの報告に、何をきっかけに動くかと、1 回の実行でおよそ何分使うかを書く。
- 役目を終えたワークフローは、残さずに消す。

## 当てはまらないとき

- ユーザーが消費の増える構成（OS の追加、定期実行の頻度など）をはっきり指示したときは、それに従う。消費がどれだけ増えるかを報告に添える。
- セルフホストランナーで動かすジョブには、実行時間の節約は当てはまらない。保存容量の節は当てはまる。
